## A1. Alibaba Cluster Trace

**Repository:** github.com/alibaba/clusterdata hosts multiple traces:
v2017, v2018, gpu-v2020, microservices-v2021, microservices-v2022,
microarchitecture-v2022
(source: https://github.com/alibaba/clusterdata).

### Which trace to use for sequence mining of discrete failure events

The two viable candidates are **cluster-trace-v2018** and
**cluster-trace-gpu-v2020**. The 2017 trace is small (~1,300 machines,
12 hours); the microservices traces target call-graph / latency analysis
rather than task-status transitions.

**cluster-trace-v2018 (RECOMMENDED for CPU/batch-workload failure mining)**
- Scale: ~4,000 machines, 8 days, ~280 GB uncompressed / ~98 GB compressed;
  largest file `container_usage` ~28 GB, smallest `machine_meta` 92 KB
  (source: https://raw.githubusercontent.com/alibaba/clusterdata/master/cluster-trace-v2018/trace_2018.md).
- Six tables: `machine_meta`, `machine_usage`, `container_meta`,
  `container_usage`, `batch_task`, `batch_instance`
  (source: https://raw.githubusercontent.com/alibaba/clusterdata/master/cluster-trace-v2018/schema.txt).
- Discrete-status fields: `status` in `batch_task`, `batch_instance`,
  `container_meta`, and `machine_meta` (source: same schema.txt).
- Status vocabulary (documented for v2017, carried into v2018 batch tables):
  `Ready | Waiting | Running | Terminated | Failed | Cancelled | Interrupted`
  (source: https://github.com/alibaba/clusterdata/blob/master/cluster-trace-v2017/trace_201708.md).
- Timestamp granularity: seconds (`start_time`, `end_time`); entity
  granularity ranges from machine down to individual `instance_name` within a
  `task_name` within a `job_name`.
- Download: shell script `fetchData.sh` in the repo pulls six archives from
  Aliyun OSS; two variants (mainland China vs international) are provided.
  No survey / registration currently mentioned in `trace_2018.md`.
  Historically a survey was requested; the current fetch script is public.

**cluster-trace-gpu-v2020 (better if GPU/DL-job failures are of interest)**
- Scale: 6,500+ GPUs on ~1,800 machines, ~2 months (Jul-Aug 2020)
  (source: https://raw.githubusercontent.com/alibaba/clusterdata/master/cluster-trace-gpu-v2020/README.md).
- Seven tables: `pai_job_table`, `pai_task_table`, `pai_instance_table`,
  `pai_sensor_table`, `pai_group_tag_table`, `pai_machine_spec`,
  `pai_machine_metric`; `status` field appears in the job/task/instance
  tables with vocabulary `Running | Terminated | Failed | Waiting`, and the
  README explicitly notes "only Terminated tasks are successful".
- Archive sizes total ~1.4 GB compressed (largest `pai_instance_table.tar.gz`
  663 MB).
- Download: Alibaba OSS or the GitHub mirror
  https://github.com/qzweng/clusterdata-cluster-trace-gpu-v2020-data.

## B. Prior work applying itemset / sequential pattern mining

Very few papers combine classical FIM/SPM with these two specific traces.

**Paper 1.** Ren, R.; Li, J.; Yin, Y.; Tian, S. "Failure Prediction for
Large-Scale Clusters Logs via Mining Frequent Patterns." *FICC 2020*, CCIS
vol. 1385, Springer, 2021. DOI: 10.1007/978-981-16-1160-5_13.
- Datasets: **CMRI-Hadoop, LANL-HPC, BlueGene/L logs** (NOT Alibaba,
  NOT Azure PdM).
- Algorithm: Spark-FP-Growth on event-density-based sliding-window
  transactions.
- Claim: adaptive sliding-window division + FP-Growth on long-tail event
  sequences improves failure-prediction accuracy over fixed-window baselines.
- Code/data release: not indicated.

**Paper 2 (adjacent).** Kumar et al. "Hybrid ML models for task-failure
prediction on Google cluster traces", *Computing*, Springer, 2026
(https://link.springer.com/article/10.1007/s00607-026-01718-w). Google
(Borg) trace, classifiers, no SPM. Closest task-failure-prediction analogue.

**Paper 3.** "Sequential predictive maintenance and spare parts management
with data mining methods: a case study in bus fleet", *Journal of
Supercomputing*, Springer, 2024
(https://link.springer.com/article/10.1007/s11227-024-06297-1). Uses
**PrefixSpan and Apriori** on a bus-fleet maintenance log (not Azure PdM),
demonstrating the exact `errors -> component_failure` sequence-mining shape.

**Paper 4 (adjacent).** Rosà, A. et al., and arXiv:1808.02919
"Characterizing Co-located Datacenter Workloads: An Alibaba Case Study"
(https://arxiv.org/pdf/1808.02919). Task-failure characterisation on
Alibaba 2017/2018 with statistics + ML, no FIM/SPM.

No papers surfaced that apply Apriori, FP-Growth, PrefixSpan, SPADE, GSP,
CM-SPAM or VMSP directly to (a) Alibaba `batch_instance`
Failed/Interrupted status sequences, or (b) Azure PdM `errorID -> failure`
sequences.

### Gap analysis

- **Itemset-vs-sequence head-to-head on Alibaba v2018 batch_instance
  error/interrupt/fail transitions:** no paper found. Ren 2021 does it on
  BlueGene/LANL. Clean gap.
- **PrefixSpan on Alibaba failure/retry events:** no paper found.
- **Apriori / FP-Growth / PrefixSpan on Azure PdM `PdM_errors ->
  PdM_failures`:** no peer-reviewed paper found; only Kaggle notebooks and
  one adjacent bus-fleet study. Direct gap.
- **Genuine defensible framing:** "Head-to-head evaluation of FP-Growth
  (itemset) vs PrefixSpan (sequence) on Alibaba 2018 `batch_instance`
  Failed/Interrupted transitions and on Azure PdM `errorID` sequences
  preceding component failure, with matched-control windows and identical
  support/confidence thresholds." Nothing rules this out.
- Secondary gap: **cluster-trace-gpu-v2020 status-transition sequence
  mining** appears completely untouched by the FIM/SPM literature.

## C. Practical recommendations (from scout)

**Scout recommendation:** start with Alibaba cluster-trace-v2018 because it
is real data, has a clean discrete vocabulary, and is publicly fetchable.
Use Azure PdM as a second, contrast dataset.

### Preprocessing gotchas

- Event-vocabulary explosion on long-tail event distributions (Ren 2021);
  on Alibaba, strip `task_name` DAG encoding to `task_type` to avoid vocab
  blow-up.
- Azure PdM class imbalance: `PdM_failures` is a strict subset of
  `PdM_maint`; naive support thresholds will hide failure-only patterns.
- Alibaba v2018: `disk_io_percent` uses sentinel values `-1` and `101`;
  `batch_instance.end_time` can be 0 for still-running / failed instances.
- gpu-v2020 polarity trap: `Terminated` = success, `Failed` = failure.
  Getting it wrong silently inverts every result.

### Python library recommendations

| Task | Library | Status |
|---|---|---|
| FP-Growth / Apriori | `mlxtend.frequent_patterns` | Actively maintained. |
| PrefixSpan (pure Python) | `prefixspan` (chuanconggao) | Semi-abandoned (source: https://snyk.io/advisor/python/prefixspan). |
| PrefixSpan, SPADE, GSP, CM-SPAM, VMSP, ... | SPMF (Java) via `spmf.py` or subprocess | Reference implementation set, actively maintained by Fournier-Viger. |
| Distributed FP-Growth | `pyspark.ml.fpm.FPGrowth` | Active in Spark. |

**Recommended stack:** mlxtend for FP-Growth/Apriori baselines; SPMF via
subprocess for PrefixSpan / CM-SPAM / VMSP.
